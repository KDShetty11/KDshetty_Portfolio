Pipeline Security & Zero-Standing-Admin

I secure the path from commit to production and the identities that travel it. That means SAST/DAST/secret-scanning gates across the org, supply-chain remediation, and an identity architecture designed so that long-lived keys and standing admin — the way one stolen laptop becomes a full breach — simply don't exist.

CI/CD security gates

  • SAST / DAST / secrets: Semgrep static analysis and OWASP ZAP DAST in GitHub Actions, with Gitleaks secret scanning across 15 repositories.
  • Change control: a require-review.yml workflow blocks self-approval (a non-author approval is required), and a branch-protection workflow auto-reverts direct pushes to main/uat within seconds — a compensating control I built because GitHub Free doesn't enforce branch protection on private repos.
  • Supply chain & secrets: no long-lived cloud keys in CI — GitHub OIDC mints short-lived, per-workflow credentials, and Gitleaks blocks secrets before they reach history. Dependencies are pinned and patched against known-exploitable CVEs (including transitive pins), prioritized by reachability rather than chasing every low-severity advisory.

Zero-standing-admin identity design

I designed an AWS Identity Center + GitHub OIDC target architecture to replace over-permissioned roles, persistent console users, and static keys in CI:

  • Persona permission sets: 15 Identity Center groups (Admin, Security/Cloud, Backend, Frontend, AI-ML, Data Eng, Data Science, BI, plus UAT-only intern groups), each a tag-scoped permission set — e.g. a Backend Engineer reaches only their own team's tagged resources, with explicit Deny on production-DB actions and IAM user/key creation. Session durations 1h admin / 4h engineer.
  • Just-in-time access: aws sso login — an 8-second browser flow minting credentials that auto-expire in 4 hours; offboarding revokes all sessions in seconds.
  • GitHub OIDC instead of deploy keys: CI federates into AWS with a per-repo/branch/workflow/commit-signed token; assumed task-role credentials rotate roughly every 6 hours, so no long-lived secret sits in a pipeline.

Threat-modeled end to end: RCE on one ECS task reaches only that task's tag-scoped role, CloudTrail logs it, GuardDuty flags it — blast radius: one task, one role, six hours, an estimated 80% cut in standing admin.

Audits that drove the design

The architecture came out of hands-on audits across every identity surface: an AWS IAM audit (70+ roles, 20 users, 60+ buckets → 4 Critical + 6 High, including over-broad service-account keys and a privilege-escalation pipeline role); a MongoDB Atlas audit (P0 fixes: enforce MFA, API IP-access-list, restrict employee data access; trimmed excess ORG_OWNERs); and a GitHub org audit (surfaced the private-repo branch-protection gap that the auto-revert workflow now compensates for). Codebase-level audits of the backend, frontend, and Clara mapped exactly which SDK clients break on a static-key-to-task-role migration.

Tooling I built

  • offboarding-evidence.py — a forensic tool that builds an evidence pack for a departing employee from the GitHub audit-log S3 bucket: every commit, PR, review, branch/tag, and membership change in a date range, emitted as a human-readable report plus raw JSONL. It's step 5 of the offboarding runbook.
  • Coder cloud-IDE platform — a 9-stage, reversible, dry-run-by-default deployment of a Coder control plane in AWS (private-subnet EC2, scoped IAM roles and security groups) so contractors and interns get ephemeral, monitored dev workspaces instead of source on personal machines — the core of a BYOD strategy.
  • github-traffic-monitor — a Lambda capturing clone/traffic signals to CloudWatch for visibility GitHub webhooks don't provide.
