The mandate

A healthcare SaaS handling PHI, no security team, and an account that had grown the way startups' do — broad permissions, services reachable from anywhere, encryption and logging applied unevenly. My job was to turn that into a posture I could defend to an auditor and to an attacker, without taking the product offline to do it.

A network where the data path isn't internet-reachable

The organizing principle: nothing that touches data should be directly reachable from the internet. So the only things in public subnets are the load balancer and a NAT gateway. The application containers run in private subnets, reachable only through the ALB; egress to external services goes out through NAT. The database is reached over VPC peering to MongoDB Atlas, so PHI in transit never crosses the public internet, and Atlas's allowlist is pinned to our egress address rather than left open.

At the edge, the WAF runs in default-deny allowlist mode — it permits the specific request shapes the app needs and blocks everything else, which fails safe as new routes appear, unlike a blocklist that's only as good as its last signature update. CloudFront fronts it with TLS termination and a strict header policy.

Defense in depth, chosen for a reason

  • Preventive — WAF allowlist, account-wide Block Public Access, SSE-KMS as the default for object and queue storage, and secrets in a managed store so there are no long-lived keys sitting in environment files.
  • Detective & continuous — GuardDuty for runtime threats, Macie classifying the PHI store on a schedule, Inspector scanning container images, and CloudTrail feeding Security Hub. The emphasis is on continuous evaluation: posture is checked constantly, not at audit time.
  • Data protection — encryption at rest and in transit everywhere, plus a PHI access-audit layer at the application so every read of sensitive data is attributable, satisfying HIPAA §164.312(b).

Identity & access — across AWS and Azure

I run identity on both clouds, end to end. On AWS that's Identity Center SSO and a per-service role model — each ECS task, Lambda, and pipeline gets its own least-privilege execution role scoped to exactly the resources it needs, with KMS keys and Secrets Manager entries protected by tight resource policies rather than broad grants. On the Microsoft side I administer Entra ID and Intune: employee joiner/mover/leaver lifecycle, SSO with conditional-access and MFA, device enrollment and compliance policy, and mailbox and application access management across M365. Every access boundary — IAM, Entra, KMS, secrets — I wrote and configured myself, so least privilege is enforced consistently whether a request comes from a service, a pipeline, or a person. (The zero-standing-admin design behind the AWS side is detailed under DevSecOps & Identity.)

Audit logging an insider can't quietly rewrite

Compliance is only as trustworthy as the evidence behind it, so the audit trail is designed to be immutable and independently sourced. Control-plane activity from three planes — source control, identity, and the database — is exported to an S3 bucket under Object Lock (WORM), where even an administrator can't alter or delete it within the retention window. The source-control pipeline verifies an HMAC signature on every event before it's written, so the log can't be spoofed. The result is a tamper-evident record of who did what, drawn from the systems themselves rather than from the app's own logs.

IAM remediation by class, not by ticket

The 500+ Security Hub findings I cleared mattered because of what they were, not how many. I triaged them into classes and went after the ones that actually move risk:

  • Privilege-escalation paths — roles that could PassRole into more powerful roles or carried IAM-mutating permissions, the findings that turn a foothold into account takeover. These came first.
  • Over-permissioned roles — wildcard actions and unused broad grants, scoped down to least privilege.
  • Public-access & encryption gaps — exposed resources and unencrypted stores, closed account-wide rather than one at a time.

An IAM audit across the account's roles, users, and buckets drove the work, and it ran as a phased, blast-radius-aware plan — each change weighed for what it could break, sequenced so production never went down. Closing those classes is what took SOC 2 / HIPAA gap closure to 85% in four months.

End-to-end ownership

This isn't a "review someone else's infra" role — I build and run it. I own the deployment path: containerized backend, CI to container registry to ECS with health-gated rolling deploys and rollback, the frontend build to object storage + CDN, and the standalone serverless services behind the API gateway. Infrastructure is defined as code with Terraform, so the whole estate is reproducible and peer-reviewable. I consolidated fragmented DNS into one zone, issued and wired TLS across every host, and stood up the WAF, CORS, and header posture in front of it all. App, infrastructure, network, identity, and pipeline are one person's remit — mine.
