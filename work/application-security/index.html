Rebuilding the App's Security Posture

I own secure development across the whole platform — an Express/Mongo backend, a React SPA, a FastAPI/Bedrock LLM agent, and the ETL pipelines behind them. The work that mattered wasn't bumping dependencies; it was re-architecting how the app authenticates, authorizes, and trusts input, then proving it against a third-party pentest with a clean result.

The auth & session rebuild

Before: the SPA minted JWTs and kept them in the browser where JavaScript could read them, the token payload carried each user's full organization list, sessions had no server-side kill switch, and the verifier didn't pin an algorithm. Net effect: a single XSS meant full account takeover, a stolen token stayed valid until expiry, logout didn't actually end a session, and the token was trivially bloated and tamper-curious.

What I changed:

  • Moved access and refresh tokens into HttpOnly + Secure + SameSite cookies so client-side script can no longer read them — XSS stops being a credential-theft primitive.
  • Scoped a parent cookie domain so the SPA and API subdomains share authentication cleanly, without widening cookie scope further than needed.
  • Pinned JWT to HS256 at every verification site, killing alg:none / algorithm-confusion forgery.
  • Slimmed the token to a user identifier plus a sessionVersion claim; logout, password change, role removal, or a suspected breach increments the version and instantly invalidates every outstanding token — stateless revocation, no blocklist to operate.
  • Added double-submit CSRF, because moving auth into cookies reintroduces CSRF — closed the door I'd just opened.

Authorization decided server-side, never by the client

The most dangerous bugs weren't exotic — they were endpoints that trusted the caller. A request could carry an orgId in its body, or a guessable resource id, and the server would honor it: cross-tenant reads of another customer's compliance data, mutations of another org's records, even deletion of another tenant's stored images by passing their id. Classic IDOR / BOLA, and in a multi-tenant healthcare platform that's a breach.

I fixed the pattern, not just the instances: a single assertInScope authorization primitive that derives the tenant from the authenticated principal and refuses anything the caller tries to assert in the request body. It's enforced in the service layer on every cross-tenant path, privileged actions are gated by role, and post-mutation refetches were rewritten to stay tenant-scoped so no read could leak sideways. The rule is simple and absolute: authorization is computed from identity, never from attacker-controllable input.

Treating all input as hostile

  • Validate at the edge: strict DTO/schema validation (type, shape, length, allowlisted enums) before input reaches business logic or the database — reject early, fail closed.
  • Encode for the sink: context-aware output encoding (HTML body vs attribute vs URL) and DOMPurify on every render sink, so data authored by one user can never execute in another's browser.
  • Neutralize injection: user input used inside Mongo $regex is literal-escaped to kill ReDoS; query construction avoids operator injection; uploaded/derived filenames are stripped of CRLF and path-traversal before they become HTTP headers or storage keys.
  • Contain server-side fetchers: the PDF renderer and file proxies are allowlisted so they can't be steered at internal services or the cloud instance-metadata endpoint — SSRF closed at the egress, not just the input.

Reusable frameworks, not one-off patches

The durable value is the controls that make whole vulnerability classes structurally impossible — build once, enforce everywhere:

  • Double-submit CSRF middleware with constant-time comparison and a careful exempt-list for session-boundary routes.
  • PHI audit middleware that records every access to PHI-handling routes (actor, org, path, status, request-id) for HIPAA §164.312(b).
  • Tiered rate limiting — global, per-route auth limits, and per-target limits on password-reset / MFA — to blunt brute force, credential stuffing, and MFA-fatigue.
  • Single-use, hashed tokens for email links and password resets (jti + TTL, stored hashed), and an S3 key path-traversal guard on anything that builds a storage key from user input.

A systematic OWASP review — not just what a scanner flagged

I reviewed the platform category by category against a decade of OWASP Top 10 lists (2013 → 2017 → 2021) and the OWASP Top 10 for LLM Applications — so coverage was driven by a threat model, not by whatever a tool happened to surface. A few of the mappings:

  • A01 Broken Access Control → the assertInScope / RBAC work above.
  • A02 Cryptographic Failures → HttpOnly cookies, HS256 pinning, hashed reset tokens, TLS-only transport.
  • A03 Injection → ReDoS escaping, NoSQL operator safety, context-aware output encoding.
  • A05 Security Misconfiguration → security headers / CSP, debug endpoints and API docs disabled in production.
  • A07 Identification & Auth Failures → MFA rate-limiting, session revocation, single-use links, removal of a hardcoded auth bypass.
  • LLM01 Prompt Injection → untrusted-content envelope around tool output; LLM02 Insecure Output Handling → output sanitizer; LLM06 Sensitive Disclosure → Safe Harbor PHI redaction; LLM08 Excessive Agency → per-tool RBAC and scoped tools.

The catalog of 127 documented fixes — each written up with its attack scenario, exploit, fix, and post-fix invariant — is the output of that sweep, not a list of dependency bumps.

The result

Independent third-party Web Application & API pentest: 0 Critical, 0 High, 2 Medium, 4 Informational. No PHI exposed.

  • The two Mediums were a refresh-token replay window (closed by the sessionVersion revocation framework) and a flagged public bucket that proved a false positive — it belonged to a different cloud account, demonstrated with an access-denied check.
  • Informational items (CSP delivery, transport headers, a WebSocket origin allowlist) were closed in the following release.
