Securing a Healthcare LLM Agent

Clara is an agent that reads clinical content and calls dozens of tools across a HIPAA platform on a user's behalf. That combination — autonomy, untrusted input, PHI, and a model with no concept of tenant boundaries — breaks the assumptions ordinary app-security controls rely on. I designed the permission model, the tenant isolation, and the prompt-injection and cost defenses that let it operate safely.

Why an agent is a different threat model

A traditional API does what the request says; an LLM agent decides what to do and then acts. It ingests documents, tickets, and survey text that an attacker may have authored, it can chain tool calls, and the model underneath has no idea which tenant it's serving. Three failure modes dominate, and none are solved by prompt engineering: cross-tenant data access through the tools, indirect prompt injection from content the agent reads, and PHI leakage into context, logs, or responses. I treated the model as untrusted and put the controls around it.

Least privilege for an autonomous caller

Access resolves through three scopes — role → organization → conversation — and the most restrictive always wins. The conversation scope lets a user voluntarily run read-only even when their role allows more; the org scope is an admin ceiling; the role is the floor. On top of that, each of the 42 tools carries its own RBAC entry, so a destructive or risk-mutating tool needs a manager/admin role and an explicit confirmation step, while a read tool doesn't. The point: the agent can only ever exercise the intersection of what the user, the org, and the conversation permit — a confused-deputy or runaway tool-chain still can't exceed the caller's real authority.

The core insight: isolate the tenant below the model

You cannot trust an LLM to scope its own queries — a clever prompt will eventually talk it into "show me everything." So tenant isolation lives beneath the model, where the model can't reach it:

  • MongoDB: a tenant $match stage is prepended to any pipeline the agent produces — whatever the LLM authors runs only inside the caller's organization.
  • Athena: generated SQL must carry the caller's facility identifier; queries that don't are rejected before execution.
  • Object storage: image and file access is locked to an {org}/{user}/ key prefix derived from the session, never from a parameter the model can set.

The model can ask for anything; the data layer will only ever return one tenant's data. That's the difference between "we told the AI to be careful" and an enforced boundary.

Prompt injection & output handling

The model can't reliably tell data from instructions, so I stopped asking it to. Tool results come back wrapped in an explicit untrusted-content envelope, and one real injection vector — a user forging a [System: ...]-style preamble to smuggle instructions — was closed by moving that state server-side so the user's text can never occupy a trusted slot. On the way out, every response passes an output sanitizer (strip script/iframe/event-handlers, rewrite dangerous URL schemes) applied at both the stream emit and again before persistence — defense in depth against stored XSS through generated content.

Session integrity & cost as an attack surface

The agent runs over long-lived WebSocket sessions, which is its own attack surface. Each connection authenticates with a single-use handshake ticket (short TTL), and every message thereafter re-binds to the authenticated identity — a swapped or replayed token terminates the socket rather than silently continuing. The JTI replay cache was moved off in-process memory into a shared store so the guarantee holds across replicas, not just one instance.

And a problem unique to LLMs: an attacker who can make the agent work can make you pay. I treated spend as a control — a Bedrock spend cap and per-user session quotas bound the blast radius of denial-of-wallet, and the Bedrock agent alias is pinned (no $LATEST) so model behavior can't shift underneath the safety testing.

PHI redaction & proving the invariants

Because a model's context and a provider's logs are places PHI can escape, redaction happens before content reaches the model: an allowlist-based, per-data-model field classification that blocks the full set of HIPAA Safe Harbor 18 identifiers, feature-flag gated for per-environment enforcement. None of this is trustworthy unless it's continuously verified, so the boundaries are encoded as tests — permission resolution, organization isolation, and cross-org denial are part of the suite, so a regression that would open a tenant boundary fails the build, not the pentest.

Beyond securing the agent, I also built the AI/data systems around it — a topic-clustering pipeline over compliance documents, a knowledge-graph visualization, a transcription pipeline (presigned upload → speech-to-text → medical-vocabulary formatting), and AI pre-fill for clinical forms — so I secure these systems as someone who builds them.
